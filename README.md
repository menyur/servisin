# Fixify — Platform Pemesanan Jasa Serba Bisa

Aplikasi full-stack (Next.js App Router + Supabase + Tailwind CSS) untuk platform booking jasa: **Service AC, Tukang Rumah, Service Kendaraan, Kebersihan & Laundry** — dengan panel admin lengkap, dasbor teknisi, pembayaran terverifikasi, notifikasi push, dan aplikasi Android.

> 🔐 Keamanan (RLS, storage, env): lihat [docs/security.md](docs/security.md)
> 🚀 Persiapan rilis ke publik (prasyarat, runbook, rollback): lihat [docs/go-live-checklist.md](docs/go-live-checklist.md)

## Fitur utama

- **Landing page + wizard booking** multi-step (pilih layanan → varian ukuran → jadwal → alamat → pembayaran), dengan harga per varian (mis. ukuran PK AC)
- **Lacak pesanan publik** via kode booking (`/track`) — tanpa login, hanya data aman
- **Dashboard pelanggan**: riwayat pesanan, konfirmasi pembayaran + upload bukti (privat), cetak/unduh struk PDF, arsip struk, voucher, beri penilaian teknisi, laporan, pengaturan notifikasi
- **Dashboard teknisi**: tugas masuk, ubah status pekerjaan, saldo dengan komisi per teknisi (setor/tarik dengan persetujuan admin + bukti transfer), histori pendapatan, dan **syarat saldo > 0 untuk mengambil pekerjaan baru** — saldo 0/minus mematikan tombol Ambil beserta alasannya ([aturnya](docs/balance-rule.md), ditegakkan server `claim_job`, bukti hidup `npm run verify:claim`)
- **Panel admin**: pesanan (filter/sort/badge), konfirmasi & penolakan bukti bayar, kelola layanan + **varian ukuran**, pendaftar teknisi (approve + verifikasi KTP), laporan masuk, penilaian teknisi (siapa pengguna yang menilai + rekap per teknisi; satu baris = satu penilaian, lengkap dengan ulasan bila ditulis), kartu pesanan menampilkan rincian voucher yang dipakai (kode + nominal + asal), histori per pelanggan/teknisi, ringkasan keuangan, kelola voucher, kelola saldo teknisi, **saldo aktif per teknisi + laporan potongan biaya aplikasi** (tab "Saldo Aktif"), **menetapkan biaya aplikasi** yang ditagihkan ke pelanggan (tab "Biaya Aplikasi" — satu angka untuk harga web, RPC aplikasi, komisi teknisi, dan panduan; berlaku untuk pesanan baru), unduh CSV + laporan bulanan otomatis
- **Notifikasi**: email (Resend — simulasi otomatis tanpa API key) + **Web Push** (VAPID) dengan preferensi per peristiwa
- **PWA + aplikasi Android**: ter-install dari Chrome, plus APK siap unduh di `/unduh`

## Tech stack

- **Frontend**: Next.js (App Router), Tailwind CSS, Lucide Icons
- **Backend**: Next.js Server Actions (tanpa server terpisah)
- **Database & Auth**: Supabase (PostgreSQL + Supabase Auth, RLS di semua tabel)
- **Email**: Resend · **Push**: Web Push (VAPID) · **Payment**: Midtrans Snap (mode simulasi otomatis tanpa API key)
- **Lint**: ESLint 9 lewat flat config `eslint.config.mjs` (preset `eslint-config-next`) — `npm run lint`, dijalankan otomatis oleh workflow **Web Lint**

## 1. Siapkan project Supabase

1. Buat project di [supabase.com](https://supabase.com) (gratis).
2. **SQL Editor** → jalankan `supabase/schema.sql`, lalu `supabase/seed.sql`.
3. Jalankan juga file `supabase/migrate-*.sql` dan `supabase/fix-*.sql` (semuanya idempoten) — atau setidaknya yang terbaru: `fix-security-audit.sql`, `migrate-push-subscriptions.sql`, `migrate-notification-prefs.sql`, `migrate-technician-balance.sql`, `migrate-service-options.sql`, `migrate-reviews.sql`, `migrate-reports.sql`, `migrate-vouchers.sql`, `migrate-receipt-archives.sql`, `migrate-monthly-report-archives.sql`, `migrate-approval-status.sql`, `migrate-commission-rate.sql`, `migrate-technician-ktp.sql`, `fix-technician-skill-matching.sql`.
4. Buat bucket Storage: jalankan `node scripts/setup-storage.mjs` (butuh service role key di `.env.local`) — lalu jalankan bagian policy di `supabase/setup-storage-buckets.sql`.
5. Salin **Project URL** dan **anon public key** dari Settings → API.

## 2. Jalankan aplikasi

```bash
npm install
cp .env.example .env.local
# isi minimal: NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY
npm run dev
```

Buka `http://localhost:3000`. Script lain: `npm run build` (produksi), `npm run lint` (ESLint 9 — perintah sama yang dijalankan CI), `npm run clean:cache` (laporan ukuran cache build lokal: `.next`, `flutter_app/build`, `.dart_tool`, `android/.gradle`; tambahkan `-- --yes` untuk menghapusnya), `npm run cleanup` (bersihkan data uji di database, bukan cache).

## 3. Akun admin pertama

1. Daftar lewat `/register`, lalu di Supabase **Table Editor → profiles** ubah kolom `role` jadi `admin`.
2. Login ulang — menu **Admin** muncul di navbar.

## 4. Env produksi (Vercel)

Semua variabel di `.env.example` yang berakhiran rahasia (tanpa `NEXT_PUBLIC_`) wajib diisi di Vercel → Settings → Environment Variables: `RESEND_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, dan `FCM_SERVICE_ACCOUNT_BASE64` (push Android — tanpa ini push APK dilewati tanpa error, lihat [src/lib/fcm.js](src/lib/fcm.js)). Yang `NEXT_PUBLIC_*` (termasuk `NEXT_PUBLIC_VAPID_PUBLIC_KEY`) baru berlaku setelah **redeploy**. Rinciannya di [docs/security.md](docs/security.md#4-env--apa-yang-publik-apa-yang-rahasia).

**Notifikasi push & tugas terjadwal.** Antrean `push_outbox` tidak lagi bergantung pada aplikasi dibuka, dalam tiga lapis. **Database (utama, tercepat):** buat **Database Webhook** di Supabase — Integrations → Database Webhooks → tabel `push_outbox`, event *Insert*, HTTP POST ke `https://servisin-six.vercel.app/api/push-worker`; worker dipanggil seketika setiap baris antrean masuk sehingga notifikasi chat tidak menunggu jadwal apa pun. Berkas [supabase/migrate-push-scheduler.sql](supabase/migrate-push-scheduler.sql) menyiapkan hal yang sama plus `pg_cron` tiap menit sebagai penyapu kegagalan (sekali tempel di SQL Editor; keduanya memakai `pg_net`). **Cadangan:** [push-sweeper.yml](.github/workflows/push-sweeper.yml) menyapu dari CI dan sekaligus menjalankan gate notifikasi — tanpa rahasia, tapi cron GitHub Actions tidak tepat waktu (umumnya tertunda 15 menit–2 jam), jadi ia jaring pengaman, bukan penjadwal utama. Tidak ada yang memakai jatah cron Vercel (Hobby: 2 tugas, masing-masing hanya sekali sehari). Kesiapan produksi diperiksa `npm run verify:notif-env` — env service role/FCM/VAPID harus terbaca **di deployment aktif**, `notifikasi.fcmReady` harus true, dan uji kirim FCM sungguhan harus dijawab Google sebagai error level token. Endpoint cron menerima `x-cron-secret`, `?secret=`, dan `Authorization: Bearer <CRON_SECRET>` (yang dikirim Vercel Cron) — dijaga [src/lib/cron-auth.js](src/lib/cron-auth.js) + `npm run verify:cron-auth`.

**Notifikasi progres pesanan dari aplikasi.** Aplikasi teknisi mengubah pesanan lewat RPC Supabase langsung (`claim_job`, `set_job_status`), bukan lewat dashboard admin — dan RPC hanya menulis DB, sedangkan kunci VAPID/FCM ada di server web. Kalau tidak dijembatani, aksi push di [src/app/actions/admin.js](src/app/actions/admin.js) tak pernah jalan dan pelanggan **tidak** menerima push "teknisi ditugaskan", "pengerjaan dimulai", atau "pesanan selesai" selama teknisi bekerja dari aplikasi. Karena itu aplikasi memanggil [src/app/api/notify-booking-status/route.js](src/app/api/notify-booking-status/route.js) (fire-and-forget) begitu RPC sukses; route itu memverifikasi Bearer token + keadaan pesanan sebelum mengirim. Dijaga `npm run verify:booking-status` (jalankan dengan dev server hidup).

**Penerima notifikasi "pekerjaan baru".** Pemilihan penerima berlapis (fail-open) lewat `selectJobTargets` di [src/lib/skill-match.js](src/lib/skill-match.js): *area + keahlian* → *keahlian saja* → *semua teknisi approved*. Alasannya: filter area mencocokkan TEKS `service_area` di dalam alamat pesanan, dan alamat tanpa nama area (mis. "griya reang indah blok B2" untuk teknisi ber-area "Serang") membuat dulu TIDAK ADA penerima sama sekali sehingga pekerjaan menggantung. Aplikasi (jobs_screen) memakai aturan yang sama agar daftarnya konsisten. Dijaga `npm run verify:job-target`. Notifikasi "pekerjaan baru" tidak bergantung pada pin map — pin hanya dipakai untuk jarak/rute (lihat [src/lib/job-offer.js](src/lib/job-offer.js)).

**Penilaian teknisi & voucher insentif.** Menilai cukup dengan bintang — ulasan tertulis OPSIONAL, dan tolak-ukur-nya bukan "kolom boleh NULL": web + aplikasi sengaja mengirim **string kosong** karena `reviews.comment` di produksi bisa NOT NULL (tabel dibuat lewat Table Editor) — mengirim `NULL` membuat penilaian tanpa ulasan gagal tersimpan. [supabase/migrate-reviews-comment-nullable.sql](supabase/migrate-reviews-comment-nullable.sql) disediakan hanya untuk paritas skema. Setiap penilaian BARU menerbitkan voucher Rp 2.000 otomatis (satu per pesanan, dijaga unique index). Dijaga `npm run verify:review-voucher`.

**Notifikasi email ke admin.** Delapan peristiwa dikirim ke email admin: pesanan baru masuk, laporan baru (pelanggan/teknisi), pengajuan setor saldo, pengajuan tarik saldo, pendaftaran teknisi, pendaftaran pelanggan, bukti pembayaran pelanggan, dan teknisi melepas tugas. Secara bawaan penerimanya **semua admin** — admin mana yang menerima tiap jenis peristiwa bisa diatur (paragraf berikutnya). Isi email selalu dibangun server **dari database** (klien hanya menyebut id, jadi isinya tidak bisa dipalsukan) lewat satu pintu [src/lib/admin-email.js](src/lib/admin-email.js). Ada dua jalur yang dipakai otomatis:

- **Langsung.** Aplikasi Flutter memanggil [src/app/api/notify-admin-event/route.js](src/app/api/notify-admin-event/route.js) (fire-and-forget) setelah membuat pesanan/laporan/setoran; route memverifikasi Bearer token **dan** bahwa barisnya memang milik pemanggil (RLS) sebelum mengirim. Server action web mengirim lewat helper yang sama. Jadi lima peristiwa tetap terkirim tanpa penyiapan database tambahan.
- **Antrean (disarankan).** Jalankan [supabase/migrate-admin-email-outbox.sql](supabase/migrate-admin-email-outbox.sql) sekali di SQL Editor: trigger DB menulis satu baris ke `admin_email_outbox` untuk **setiap** sumber (termasuk **pendaftaran akun dari aplikasi/web**, yang tidak punya sesi untuk memanggil route), lalu worker [src/app/api/admin-email-worker/route.js](src/app/api/admin-email-worker/route.js) menyapu batch (FOR UPDATE SKIP LOCKED). Saat antrean aktif, jalur web otomatis beralih ke antrean sehingga email tidak pernah dobel. Pemicu tercepat: **Database Webhook** tabel `admin_email_outbox` event *Insert* → `https://servisin-six.vercel.app/api/admin-email-worker`; berkas migrasi itu juga memasang trigger `pg_net` (instan) + `pg_cron` tiap menit sebagai penyapu kegagalan.

**Kegagalan kirim tidak lagi hilang diam-diam.** Sesudah outbox, jalankan [supabase/migrate-admin-email-failures.sql](supabase/migrate-admin-email-failures.sql): `take_admin_email_batch` berhenti **menghapus** baris yang kehabisan percobaan, dan setiap kegagalan menuliskan **alasan dari penyedia email** + waktu percobaan terakhir pada barisnya (`last_error`, `last_attempt_at`, `failed_at`). Jejaknya dibaca server dengan kunci service role lalu tampil di tab **Notif Email Admin** — kartu *Email yang gagal terkirim* berisi jenis peristiwa, alasannya, dan tombol **Coba lagi** (baris dikembalikan ke antrean setelah penyebabnya diperbaiki) maupun **Buang**. `/api/health` melaporkan `email.failedCount` + `email.lastFailedAt` + `email.queueCount` **tanpa** mempublikasikan teks alasannya (endpoint publik). Baris gagal disimpan 30 hari lalu dibersihkan otomatis. Tanpa migrasi itu perilaku lama tetap berlaku — dan di situ letak pelajarannya: pada 16 Okt 2026 kunci Resend di deployment tidak sah sehingga **semua** email admin gagal, tetapi antrean tampak kosong, `resendReady` tetap `true`, dan sebabnya hanya ada di log Vercel. Dijaga `npm run verify:admin-email` (bagian B5 memeriksa rangkaian ini, bagian C memanggil RPC + kolomnya langsung).

**Kuota/rate limit ≠ email hilang.** Sesudah failures, jalankan [supabase/fix-admin-email-macet-dan-kuota.sql](supabase/fix-admin-email-macet-dan-kuota.sql). Latarnya kejadian 16 Okt 2026 yang terbaca dari database produksi: 10 email gagal dengan alasan `daily_quota_exceeded` dari Resend, dan 11 baris lain macet di `attempts = 5/5` **tanpa** `failed_at` — tidak bisa diklaim lagi (`attempts < max_attempts` gagal), tidak muncul di panel, tetapi ikut terhitung sebagai "antrean" di `/api/health`. Penyebabnya sama: satu baris yang gagal diklaim ULANG oleh tiap ping (trigger `pg_net`, cron tiap menit, aplikasi, panel) sementara permintaan pertama masih berjalan, sehingga lima percobaan habis dalam ~4 detik dan gangguan sementara berubah menjadi permanen. Migrasi itu menambahkan kolom `not_before` (lease 5 menit saat klaim, jadi tidak ada kiriman ganda dan percobaan tidak dibakar beruntun), **menyembuhkan** baris macet (ditandai gagal beserta alasannya supaya muncul di panel dengan tombol *Coba lagi*), dan tiga RPC jejak yang dipilih worker: `defer_admin_email` (penolakan sementara dari penyedia — kuota harian menunggu reset tengah malam UTC — dengan claim **dibatalkan** sehingga percobaannya tidak terbuang), `fail_admin_email` (+ `p_delay_seconds`: jeda **bertingkat** 5 mnt → 15 mnt → 1 jam → 3 jam), dan `give_up_admin_email` (email **sudah** terkirim tetapi barisnya gagal dihapus: ditandai menyerah supaya tidak jadi email dobel — inilah salah satu sumber baris macet). Kebijakannya hidup di [src/lib/email-retry.js](src/lib/email-retry.js) sebagai modul **murni** yang diuji langsung, bukan hanya diperiksa teksnya; worker juga kini memeriksa galat `complete_admin_email` (dulu diabaikan, sehingga baris yang emailnya terkirim tetap tinggal dan dikirim ulang sampai percobaannya habis). `take_admin_email_batch(0)` sekarang benar-benar mengambil **0 baris**, supaya pemeriksa/CI bisa membuktikan RPC-nya ada tanpa mengklaim antrean nyata (probe lama justru menaikkan `attempts` baris sungguhan setiap kali dijalankan).

**Kenapa email berstatus `failed` padahal Resend sudah "menerima".** Diperiksa langsung ke akun Resend (17 Okt 2026, 376 email): pada 16 Okt semua kiriman sejak 14:36 UTC berakhir `last_event: failed` dengan **`message_id` kosong** — artinya pesannya tidak pernah diserahkan ke penyedia pengiriman, jadi bukan inbox penerima yang menolaknya. Tiga dugaan yang wajar sekaligus gugur: autentikasi domain sehat (DKIM & SPF `fixify.id` `verified`, `sending: enabled`), bounce bukan sebabnya (satu-satunya bounce bulan itu tanggal 15 Okt), dan reputasi pengirim tidak menunjukkan gejala. Penyebabnya **kuota pengiriman HARIAN habis** — Resend menjawab `daily_quota_exceeded: You have reached your daily email sending quota.`, dan hari itu terkirim 195 email yang **149 di antaranya (76%) berasal dari data uji** (jam 13:00 saja 141 email). Sekarang kegagalan kuota tidak lagi disamarkan sebagai masalah kunci/domain: `npm run verify:email-send` dan `verify:email-doctor` menyebutnya sebagai kuota + perkiraan waktu pulihnya (`pesanKuotaHarian` di [scripts/lib/email-health.mjs](scripts/lib/email-health.mjs), memakai pengenalan pola yang sama dengan kebijakan percobaan ulang di [src/lib/email-retry.js](src/lib/email-retry.js)).

**Data uji tidak lagi menyentuh kuota produksi — di SELURUH jalur.** Sebelumnya penyaringan hanya ada di worker antrean email admin, jadi jalur lain tetap mengirim: push web/FCM ke akun probe, email pelanggan/teknisi ke `…@example.invalid`, dan email admin lewat jalur LANGSUNG (sebelum migrasi antrean). Aturan satu-satunya sekarang di [src/lib/email-uji.js](src/lib/email-uji.js) dan dipasang di tiga tempat: **penerima email** dibuang dari daftar di `sendMail` ([src/lib/email.js](src/lib/email.js)) sehingga tidak ada satu pun panggilan Resend untuk akun uji; **akun tujuan push** dilewati oleh [src/lib/notify.js](src/lib/notify.js), [src/lib/push.js](src/lib/push.js), dan [src/lib/fcm.js](src/lib/fcm.js); **sumber peristiwa** diperiksa di antrean admin DAN di setiap jalur langsung (`notifyAdminsOrDirect(..., { sumberEmail })`, bukti pembayaran, penarikan saldo, pelepasan tugas). Baris antrean milik akun uji tetap dibereskan tanpa kiriman (email admin maupun push), jadi percobaannya tidak terbakar. Dijaga `npm run verify:uji-guard` — probe **offline** yang memanggil gerbangnya sungguhan (dengan klien tiruan) sekaligus membaca sumber kode untuk membuktikan tak ada berkas pengirim email admin yang lupa dipasangi gerbang; skrip diagnostik yang memang ingin mengirim ke alamat uji (mis. `verify:email-send` ke `delivered@resend.dev`) menyalakan `EMAIL_UJI_DIIZINKAN=1`.

**Email yang ditolak SEMENTARA tidak hilang, walau bukan email admin.** Jalankan [supabase/migrate-email-outbox-umum.sql](supabase/migrate-email-outbox-umum.sql): tabel `email_outbox` menyimpan pesan yang SUDAH DIRENDER (penerima + subjek + html + lampiran) ketika penyedia menolak karena kuota/rate limit, lalu [src/lib/email-antrean.js](src/lib/email-antrean.js) mengirimnya ulang setelah jendela jeda lewat — disapu dari route yang sudah ada ([src/app/api/admin-email-worker/route.js](src/app/api/admin-email-worker/route.js)), jadi tidak perlu penjadwal baru; kebijakan jedanya modul yang sama dengan antrean admin (`email-retry.js`), dan isinya hanya bisa dibaca service role (RLS menolak semua). Yang **sengaja tidak** diantrekan: email bertautan berbatas waktu (reset kata sandi, verifikasi pendaftaran, konfirmasi hapus akun) — tautannya kedaluwarsa dalam 1 jam sementara jendela kuota bisa ~10 jam, jadi email terlambat justru menyesatkan; jalur itu tetap langsung dan kegagalannya dilaporkan ke pengguna. Tanpa migrasi ini perilakunya persis seperti sebelumnya (hanya dicatat di log sekali). **✅ Tabel `email_outbox` sudah aktif di produksi (17 Okt 2026)** dan jalurnya dibuktikan ujung-ke-ujung: penolakan kuota disimulasikan → baris masuk antrean (`attempts = 1`, alasan + jendela tunggu ±653 menit tertulis pada barisnya) → sapuan mengirimnya → Resend melaporkan `delivered` dan barisnya terhapus. Izinnya juga diperiksa hidup-hidup: `anon`/`authenticated` ditolak, hanya `service_role` boleh memanggil kelima RPC (`npm run verify:rpc-grants` → 132 lulus · 0 gagal).

**Penolakan yang mustahil berhasil tidak lagi dicoba berulang (reputasi pengirim).** Dipisahkan dari pemeriksaan yang sama ke API Resend: dari 100 kiriman terakhir, **17 berakhir `bounced`** — dan pemicunya bukan pelanggan, melainkan alamat uji `…@example.invalid` (domain tanpa MX) yang ikut masuk ke daftar `to`. Karena bounce menggagalkan SELURUH pesan, penerima nyata yang menemani alamat itu (`itsupprots@gmail.com`, 17×) tidak menerima notifikasinya, sementara akun pengirim mencatat bounce keras — cara tercepat merusak reputasi domain, dan reputasi buruk membuat email pelanggan sungguhan masuk spam/ditolak. Dua lapis penanganannya: (1) penerima/sumber uji sudah dibuang sebelum satu pun panggilan Resend (lihat paragraf berikutnya), dan (2) [src/lib/email-retry.js](src/lib/email-retry.js) kini mengenali alasan **MENETAP** (`alasanMenetap`: hard bounce / alamat tidak ada / domain pengirim belum terverifikasi / kunci ditolak) dan menghentikan baris antrean SEKETIKA lewat `give_up_email` / `give_up_admin_email`, bukan menghabiskannya dengan jeda bertingkat. Alasan pada baris antrean menyebut apa adanya mengapa email itu tidak diulang, jadi admin tahu yang perlu diperbaiki alamatnya (atau domainnya) — bukan menekan *Coba lagi* berkali-kali. Dijaga `npm run verify:uji-guard` (kegagalan biasa tetap berjeda bertingkat; bounce keras berhenti).

Migrasi outbox itu **wajib untuk notifikasi pendaftaran akun** (tanpa sesi, hanya trigger DB yang tahu). Dijaga `npm run verify:admin-email` — bagian live-nya **MERAH sampai migrasi dijalankan** (sengaja, seperti gate bukti setor); bagian ujung-ke-ujung jalur aplikasi dilewati bila dev server tidak hidup. Email benar-benar sampai hanya bila `RESEND_API_KEY` terisi di deployment web; tanpa itu isinya hanya tercetak di log server. Selain itu alamat pengirim (`EMAIL_FROM`) harus memakai **domain terverifikasi** di Resend — domain uji `resend.dev` hanya bisa mengirim ke email pemilik akun. Cek kesiapan email produksi kapan pun dengan `npm run verify:email-env` (read-only; memeriksa `/api/health`), dan buktikan pengiriman nyatanya dengan `npm run verify:email-send` — mengirim lewat jalur produksi ke alamat uji Resend (`delivered@resend.dev`, tidak mengirimi inbox siapa pun) dan lulus hanya bila Resend mengembalikan id pesan. Untuk pertanyaan "kenapa email belum jalan?" pakai `npm run verify:email-doctor`: satu perintah yang menggabungkan kesiapan env produksi, **status domain pengirim**, **riwayat kiriman nyata**, dan uji kirim nyata, lalu menutupnya dengan **satu baris** masalah tersisa (`nilaiEmail`/`nilaiKirim` dipakai bersama dari [scripts/lib/email-health.mjs](scripts/lib/email-health.mjs) agar penilaiannya tidak mungkin menyimpang). **Bagian [2b] menjawab "kenapa `last_event`-nya `failed` padahal Resend sudah menerima?"** — satu-satunya bagian yang membaca pesan yang SUDAH berangkat (`GET /emails`, read-only, 100 terakhir; `--no-riwayat` melewatinya): ia memisahkan **`failed` tanpa `message_id`** (ditolak SEBELUM diserahkan — kuota harian/kunci/domain, bukan masalah inbox penerima) dari **`bounced`/`failed` dengan `message_id`** (gagal di jalan), dan — yang paling penting — membedakan **alamat uji sebagai PEMICU bounce** dari **penerima nyata yang hanya IKUT TERBAWA** di pesan yang sama. Tanpa pembedaan itu, pemeriksaan ini akan menuduh `itsupprots@gmail.com` yang tidak bersalah; dengan itu, kerugian sesungguhnya terlihat: penerima nyata yang kehilangan notifikasi karena menemani alamat uji. Temuannya dicetak beserta sebab + langkahnya, dinyatakan sebagai **historis** (beserta jendela waktunya) supaya kegagalan kemarin yang sudah ditangani tidak terbaca sebagai masalah yang masih berjalan, dan diangkat ke baris simpulan bila ada. **Status domain ditanyakan ke Resend sendiri** (`GET /domains` + `GET /domains/:id`, read-only) selama `RESEND_API_KEY` terbaca — dan itu bukan kemewahan: memeriksa DNS saja bisa memberi hijau PALSU, sebab zona bisa berisi setelan klasik (MX+TXT di `send`) yang terlihat siap sementara Resend untuk domain itu justru meminta CNAME, sehingga domain tetap `pending` dan kiriman ditolak 403 ke semua penerima. Tanpa kunci, pemeriksaan DNS tetap jalan tetapi dinyatakan sebagai perkiraan, bukan bukti (`--no-api` melewati kueri API). Kalau yang kurang ternyata catatan DNS-nya, `npm run verify:email-panduan` (`verify:email-doctor --panduan`) mencetak langkah persisnya: jenis + nama host pendek, **nilai yang diminta** (dari dashboard, atau dari API bila kunci tersedia), catatan yang sudah ada tetapi salah sehingga penyebabnya tak perlu ditebak, panel DNS pemilik zona (dibaca dari nameserver domain itu), peringatan bahwa **CNAME tidak boleh berdampingan dengan MX/TXT di nama yang sama** (catatan lama harus dihapus lebih dulu — kalau tidak, CNAME-nya diabaikan), dan tombol verifikasi di dashboard Resend. Ingin sekaligus membuktikan **kedatangan**, bukan hanya penerimaan? Tambahkan `--wait=30`: skrip menanyakan status pesan ke Resend dan hanya menyebut pesan "sampai" bila statusnya `delivered`; tanpa `--wait`, `LULUS` hanya berarti Resend menerima pesan.

**Setelah mengubah catatan DNS, cuma satu perintah.** `npm run verify:email-tunggu` (`verify:email-doctor --tunggu`, bawaan 15 menit, bisa `--tunggu=30`) memantau status domain ke Resend tiap 30 detik sampai `verified`, lalu otomatis melanjutkan ke uji kirim — cocok dipasangkan dengan `--to=<inbox nyata> --wait=90` untuk membuktikan kedatangan sekali jalan. Ia juga **memicu pemeriksaan ulang di Resend** (`POST /domains/<id>/verify`, setara tombol "Verify DNS Records") supaya tidak perlu membuka dashboard — tetapi hanya bila domainnya belum bisa mengirim, sebab memicu domain yang sudah `verified`/`partially_verified` menurunkannya sementara ke `pending` dan kirim yang tadinya jalan bisa ditolak 403 selama pemeriksaan. Karena itu `partially_verified` (mengirim jalan, tanpa server cadangan) dianggap cukup untuk lanjut dan dinyatakan apa adanya. Kalau statusnya `failed`, menunggu dihentikan lebih awal; kalau waktu habis, uji kirim **dilewati** dan alasannya dicetak, bukan dicoba lalu dilaporkan sebagai kegagalan pengiriman. Mode ini butuh `RESEND_API_KEY` (tidak bisa digabung `--no-api`). Bonus dari mode ini: ia menangkap **sisa catatan lama** yang tidak dikeluhkan siapa pun — `MX`/`TXT` dari setelan klasik yang masih menumpang di nama ber-CNAME (tidak sah menurut RFC 2181, dan membuat jawaban DNS berbeda antar resolver walaupun Resend sudah bilang `verified`). **Tetapi justru di sini pernah terjadi salah lapor (17 Okt 2026)**: resolver **mengikuti CNAME**, sehingga jawaban `MX`/`TXT send.fixify.id` ikut memuat catatan milik host Resend sendiri (`MX 10 feedback.forge.rmta.net`, SPF `ip4:52.3.252.119 …`) — dan pemeriksa yang membaca jawaban tanpa melihat **nama pemiliknya** menyimpulkan zonanya kotor lalu menyuruh menghapus catatan yang justru disediakan Resend lewat CNAME itu (menghapusnya = mencabut SPF pengirim). Sekarang jawaban dipisah menurut **pemilik + jenis record** (`barisZona`/`dataZona` di [scripts/verify-email-doctor.mjs](scripts/verify-email-doctor.mjs)): yang benar-benar ada di zona dilaporkan sebagai sisa catatan, yang hanya diwarisi dilaporkan sebagai `… terbaca dari host Resend lewat CNAME … tidak ada yang perlu dihapus`. Untuk `send.fixify.id` hasilnya zona berisi **hanya CNAME** — dibuktikan langsung ke nameserver zona (`nslookup -type=TXT send.fixify.id orbit.dns-parking.com` → hanya `canonical name`, tanpa TXT/MX) — jadi memang tidak ada yang perlu dibersihkan. Bentuk jawaban DoH yang sesungguhnya dipakai sebagai fixture di `--selftest`, supaya salah lapor ini tidak bisa kembali. Jalur kirim ([src/lib/email.js](src/lib/email.js)) memeriksa `{ data, error }` dari SDK Resend, sehingga kegagalan API tidak lagi dilaporkan sebagai sukses.

**Email reset & verifikasi pendaftaran TIDAK lagi lewat mailer Supabase.** Keduanya dibuat server (`admin.generateLink` dengan service-role key — panggilan yang **tidak mengirim email apa pun**) lalu dikirim [src/lib/email.js](src/lib/email.js) lewat Resend, jalur yang sama dengan seluruh email transaksional di atas. Alasannya bukan selera: mailer bawaan Supabase Auth **menolak mengirim ke alamat yang bukan anggota tim project** dan membatasinya 2 pesan per jam ([auth-smtp](https://supabase.com/docs/guides/auth/auth-smtp)); pelanggan biasa karena itu tidak pernah menerimanya **walau** aplikasi sudah menampilkan "Tautan terkirim!" — dan pada pendaftaran efeknya lebih parah, sebab GoTrue mengirim email DI DALAM transaksi sehingga begitu kuota habis **pendaftarannya sendiri** gagal. Dijaga dua perintah: `npm run verify:reset-endpoint` dan `npm run verify:signup-endpoint` menjalankan kontrak statis + alur hermetis tanpa jaringan (admin & pengirim email tiruan), dan bila diberi `--to=<alamat>` keduanya mengirim SATU email nyata lewat jalur produksi — `verify:signup-endpoint` sekaligus memeriksa akunnya lahir dalam keadaan **belum terverifikasi**, metadata untuk trigger `handle_new_user` ikut tersimpan, lalu **menghapus akun uji itu kembali**. `npm run verify:reset-email` tetap ada, tetapi kini hanya sebagai pemeriksa jalur LAMA: ia memanggil `/auth/v1/recover` (yang sudah tidak dipakai aplikasi) dan lulus hanya bila stempel `recovery_sent_at` bertambah — itulah cara menguji mailer Supabase sendiri, mis. sesudah memasang SMTP kustom. Panduan lengkap + nilai SMTP Resend ada di [docs/email-templates/README.md](docs/email-templates/README.md), jalan keluar dari batas pengiriman Auth (naikkan batas, atau kirim sendiri lewat Resend dengan `admin.generate_link`) ada di [docs/reset-password-email.md](docs/reset-password-email.md), dan rekomendasi jalur yang paling tidak mudah macet — kode 6 digit yang diketik di aplikasi, lengkap dengan petunjuk perubahannya — ada di [docs/reset-password-otp.md](docs/reset-password-otp.md). Langkah tetap untuk menguji alur ini di APK (dari minta kode/tautan sampai berhasil masuk dengan sandi baru, beserta apa yang diperiksa di tiap langkah dan kasus tepi yang wajib dilewati) ada di [docs/prosedur-uji-lupa-password.md](docs/prosedur-uji-lupa-password.md) — dan bagian yang tidak perlu mata manusia dijalankan satu perintah: `npm run verify:reset-flow -- --to=<alamat uji>` menjalankan kontrak teks/konstanta prosedur, kontrak deep link, bukti stempel `recovery_sent_at`, dan jalur Resend, lalu mencetak laporan lulus/gagal siap-tempel (kode keluar 0/1/3; tanpa `--to`, pemeriksaan stempel dilewati dan tidak ada email yang dikirim).

**Memilih admin mana yang menerima tiap jenis peristiwa.** Panel Admin → tab **"Notif Email Admin"** menampilkan matriks peristiwa × admin; kotak yang tidak dicentang berarti admin itu **tidak** dikirimi email jenis tersebut (notifikasi di panel tetap tampil untuk semua admin, begitu juga laporan bulanan otomatis dan email ke pelanggan/teknisi). Setelannya disimpan sebagai *opt-out* di tabel `admin_notification_optouts`: admin baru maupun peristiwa baru otomatis menerima, yaitu perilaku lama — jadi tidak ada email yang diam-diam hilang. Penyaringan penerima dilakukan **di database** (`admin_emails_for_event()`), sehingga jalur web dan jalur antrean memakai aturan identik dan klien tidak bisa menambah/menghapus penerima; jalur pengiriman tidak lagi memanggil `get_admin_emails()` langsung (kalau lewat, setelan bisa dibypass). Aktifkan dengan menjalankan [supabase/migrate-admin-notification-prefs.sql](supabase/migrate-admin-notification-prefs.sql) sekali di SQL Editor — **sebelum** itu tab menampilkan peringatan dan semua email tetap dikirim ke semua admin. Dijaga `npm run verify:admin-notify-prefs` (bagian statis selalu jalan; bagian RPC live **MERAH sampai migrasi dijalankan** dan sekaligus membersihkan baris ujinya sendiri).

## 5. Aplikasi Android (APK)

Halaman **`/unduh`** menyediakan APK siap pasang + panduan instalasi dan alternatif "pasang lewat Chrome" (PWA). Status tombol diatur otomatis oleh `/api/apk-status`, yang membaca dua varian hasil CI — `fixify-arm64.apk` (HP 64-bit) dan `fixify-armv7a.apk` (HP lama 32-bit) — beserta `public/apk/manifest.json` (versi, tanggal build, ukuran, SHA-256 untuk verifikasi unduhan).

APK **tidak disimpan di Git**: berkasnya (±20 MB per varian) dipublikasikan sebagai **aset GitHub Release** pada tag bergulir `apk-latest`, dan halaman `/unduh` menaut langsung ke sana lewat [`src/lib/apk-release.js`](src/lib/apk-release.js). Sebelumnya setiap rilis menambah ±39 MB ke riwayat Git sehingga repo membengkak dan tiap clone ikut mengunduh tumpukan APK lama; sekarang Git hanya menyimpan `manifest.json` beberapa ratus byte.

Nomor rilis **naik otomatis** di setiap build: [scripts/apk-version.mjs](scripts/apk-version.mjs) menggabungkan versi dasar `version: X.Y.Z` di pubspec dengan nomor run CI (dan pagar nomor yang sudah terbit), lalu menghasilkan `versionName` `X.Y.Z.<build>` + `versionCode` <build> yang dipakai APK, AAB, dan `manifest.json` sekaligus. Jadi tidak ada lagi langkah "lupa menaikkan versi" yang membuat dua APK berbeda tampak sama.

APK **tidak dibangun manual**: [build-apk.yml](.github/workflows/build-apk.yml) membangunnya dari `flutter_app/` lewat `flutter build apk --release --split-per-abi --obfuscate --split-debug-info=build/symbols` (obfuscation + pemisahan info debug mengecilkan APK; symbol map disimpan sebagai artifact agar stack trace tetap terbaca), mengunggah asetnya ke Release, lalu bot meng-commit **hanya** `manifest.json`. Alurnya:

1. Push ke `main` yang mengubah `flutter_app/**` (atau jalankan workflow manual) → build jalan.
2. Job gate `live-probe` harus lulus lebih dulu. Tanpa secret `SUPABASE_SERVICE_ROLE_KEY` build **tertahan** (keadaan darurat: jalankan manual dengan input `skip_gate=true`).
3. Signing release dibaca dari secret `ANDROID_KEYSTORE_BASE64` + `ANDROID_KEYSTORE_PASSWORD`; bila belum di-set, APK di-sign dengan debug key dan **tidak bisa** install-over-install antar build.
4. **Simpan signing key** (mis. lewat `flutter_app/android/backup-keystore.sh`) — tanpa itu aplikasi tidak bisa diupdate di perangkat yang sudah terpasang.
5. Job menjalankan juga `flutter build apk --release --analyze-size` (build terpisah — flag itu tidak bisa digabung `--split-debug-info`) lalu meringkasnya dengan [`scripts/summarize-apk-size.mjs`](scripts/summarize-apk-size.mjs) ke halaman ringkasan job: komponen penyumbang ukuran terbesar (engine, kode Dart, dex, aset) plus paket Dart terbesar. Berkas analisisnya diunggah sebagai artifact `apk-size-report`.
6. Verifikasi cepat konfigurasi jalur unduh tanpa kredensial: `npm run verify:apk-release`.

Package ID aplikasi: **`com.fixify.app`** — harus sama di `applicationId` ([flutter_app/android/app/build.gradle.kts](flutter_app/android/app/build.gradle.kts)), OAuth Android client di Google Cloud Console, dan [flutter_app/android/app/google-services.json](flutter_app/android/app/google-services.json).

## Skema database (ringkas)
